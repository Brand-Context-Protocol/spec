# BCP 1.x and earlier to 2.0

Migration changes a package's protocol contract, never its ownership or prior
approval. Retain the original bytes, signatures, tree version and publication
identity. Publish changed bytes as a new signed revision through the existing
authorized workflow. A label change alone is insufficient.

1. Validate the old package under its original version. Record source hashes,
   missing files, provenance, owner, tree version and revision before editing.
2. Preserve all useful brand content and evidence dates. Normalize frontmatter
   to the 2.0 schema. Remove `agent_first_action` declarations from frontmatter
   and fenced YAML, recording the removed lines. Do not claim arbitrary
   equivalent prose can be detected. Do not rewrite historical source files.
3. Retain the seven established core documents. Add the required onboarding
   companion and declare all supplied daughters in the root map. If a core
   document is absent, record an explicit gap in that document; do not invent
   brand rules. Additional anti-AI, commerce, audience, product and campaign
   documents remain optional and retain their content.
4. Add a `source_coverage` record in the root: `status`, `sources`, `gaps` and
   `research_refreshed`. List actual sources and limitations. A format-only
   migration uses `research_refreshed: false`; do not reset evidence dates.
5. Migrate each claim explicitly using the table below. Retain its old status
   as `legacy_proof_status`. Preserve evidence, caveats, exact wording, dates,
   scope and owner. Review unknown or conflicting records rather than guessing.
6. Validate every file and claims block. Record the full diff and new tree
   version. Prepare and approve the exact resulting bytes where required.
7. Publish under the existing handle, independently verify source hashes and
   signatures, and verify HTML, JSON, raw sources and MCP share that revision.
   A saved draft, Git merge or HTTP success alone does not close migration.

| Old proof_status | New use_status | evidence_status | brand_approval |
| --- | --- | --- | --- |
| approved | permitted | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |
| requires_caveat | conditional | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |
| forbidden | prohibited | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |
| expired | expired | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |
| aspirational | aspirational | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |
| unknown or absent | unknown | unknown unless evidence was assessed | unknown unless explicit accountable approval is retained |

`approved` formerly mixed evidence and approval. Neither a source URL nor the
old field alone establishes evidence assessment or brand approval. `permitted`
preserves the publisher's use classification; it does not establish legal
approval or endorsement. Conditional claims require the original caveat; missing
caveats are a validation failure requiring review. Expired, aspirational,
prohibited and unknown claims are retained in the `forbidden` structured bucket
and are unavailable as factual marketing claims. In 2.0, `approved_at_launch`
is renamed `permitted`; the other buckets remain `requires_caveat` and
`forbidden`. Old canonical-claims.v1 projections remain historical v1 contracts;
they MUST NOT silently acquire these new semantics.

Duplicate names do not establish shared ownership or supersession. Select a
current handle only from ownership, provenance, content and intended example
links. Alias/archive decisions must be reversible and recorded; unresolved
duplicates remain open and are never bulk-deleted.

## Host migration (implementation guidance)

A Registry hostname change is separate from a package's 1.x-to-2.0 migration.
This section explains deployment checks; it adds no new 2.0 conformance rules
and does not require a particular Registry provider.

- Keep existing handles, authorized owners, immutable revision identities,
  source bytes, signatures and signing-key history. Changing the transport host
  alone does not require republishing or resigning a historical package. Editing
  an absolute URL inside signed source does change its bytes and requires a new
  authorized signed revision.
- For public GET/HEAD routes selected for redirection, prefer one direct HTTPS
  redirect to the final canonical URL. Preserve the exact supported path and
  relevant query parameters, including historical revision selection. Inventory
  entry pages, sections, raw files, JSON, trust, history and public-key endpoints;
  a root-and-daughter map alone may not cover the deployed read API. Test existing
  links from historical packages. Maintain documented redirect/archive coverage
  for those references when retiring the old active service. Availability of old
  links and cryptographic verification of preserved bytes are separate concerns.
- The spec's three-hop bound in §5.5.1 applies to pointer resolution; it does not
  explicitly define an HTTP redirect budget. A one-step HTTP redirect policy is
  a useful operational safeguard, not a separate normative 2.0 requirement.
- Update current domain discovery pointers explicitly: retain `file_type: pointer`
  and `canonical_bcp`, remove and record retired `agent_first_action`
  declarations, and use `bcp_version: "2.0.0"` only after validating the pointer
  under that contract. `registry_mcp` is optional for a thin pointer; retain it
  when useful and point it to the supported canonical MCP service. Pointer and
  target package versions are declared independently; a current pointer does
  not relabel its historical target. Registry-backed rich roots retain their
  separate required metadata rules.
- Recheck current account/handle/brand-domain attestation, expiry and revocation
  consistently on every new read surface. The brand domain is distinct from the
  Registry transport hostname. A transport-host change alone does not establish
  a brand-domain mismatch or require a new DNS challenge; §5.9 governs renewal,
  transfer, domain changes and revocation. Do not infer official-source status
  from a publisher-authored field or from a successful redirect.
- Treat MCP, OAuth and authenticated writes by endpoint and client capability.
  Do not assume clients follow redirects for POST, move credentials between
  hosts, or install a connector from a discovery URL. Where needed, an explicitly
  supported transitional MCP service can forward credentialless reads to the
  same authority. Test an actual existing installed client and a new canonical
  connection separately. Reauthorize through the canonical supported flow when
  changing a resource audience; verify old-audience credentials are rejected by
  the new resource, permissions and revocation remain enforced, and publishing
  requires approval of the exact resulting revision.
- For every republished package, compare revision identity, source hashes and
  independently verified signatures across raw files, JSON and actual MCP
  retrieval. Verify HTML represents those same sources; do not compare a rendered
  HTML hash to a source-file signature or assume every transport exposes identical
  headers. Preserve file-versus-package scope and trust meanings. Record the
  observed client, endpoint, revision and result before closing a cutover gate.
